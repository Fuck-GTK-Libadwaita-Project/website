操你妈的 GNOME 基金会

一份关于设计一致性、生态治理，以及用户能否决定自己电脑长什么样的公开信

自由软件最奇妙的地方，是你可以拿到源代码。至于拿到之后能不能改、改完之后算不算受支持、受支持之后能不能正常用，那就是另外三件事了。GNOME 生态尤其擅长让人理解这个区别：门是开着的，门口贴着一张纸，写着「请勿进门」。

当然，维护者有权决定自己的软件怎么设计。一个人写个计算器，决定按钮只能是灰色的，旁人没什么可说的；大不了换个计算器，毕竟全人类不至于因为不能把「等于」改成薰衣草紫就停止数学活动。

但 GTK 不是某个开发者桌面上的私人计算器。它是一套被大量应用、发行版和其他桌面环境依赖的工具包。libadwaita 也不只影响 GNOME 用户的壁纸色温，它会影响别人怎样打包、集成、主题化和维护应用。做到这里，事情就不再是「我喜欢这种圆角」了，而是「我喜欢这种圆角，所以其他人的工程排期也要对此表达敬意」。

笔者并不反对设计一致性。笔者只是对一种奇特的设计一致性有意见：它要求整个生态在外观上达成共识，却不要求生态在决定外观时拥有同等的话语权。用政治学术语说，这像是一个只负责执行、不参与制定装修规范的业主委员会；用更简单的术语说，就是你的电脑，你做不了主。


一、StopThemingOurApps：请问这个 Our 里到底有没有我？

StopThemingOurApps 这个名字很值得研究。它没有叫 StopThemingMyApps，而是用了 Our。乍看之下，这似乎体现了软件开发者的集体主义精神，仿佛所有人共同拥有这些应用。

但经过仔细研究，笔者发现这个 Our 可能采用了一种比较先进的所有权模型：开发者拥有应用的所有权，用户拥有应用的使用义务。

用户当然可以决定自己想用什么软件，但如果用户进一步决定软件应该长什么样，事情就会复杂起来。毕竟，用户只是使用者，怎么能擅自干涉所有者的设计呢？

想象一下，用户打开一个应用，发现自己不喜欢它的配色，于是尝试修改主题。应用告诉他这是不受支持的用法。用户解释自己只是想把亮白底色改成深灰色。应用再次说明，设计一致性很重要。用户问那我自己的显示器算什么？这时对话已经超出了应用的支持范围。

这不是说每个应用都必须支持任意主题。维护者可以有技术理由拒绝支持某些样式覆盖；问题是，拒绝支持和要求生态围着你的拒绝转，是两码事。一个应用不支持系统主题，是项目选择；当它所在的生态把系统主题化当成不值得支持的行为，下游才发现自己获得了一份额外工作：证明用户为什么想控制自己的屏幕。

笔者建议将主题设置里的「自定义」改名为「提交个人审美偏离申请」。点击后显示：「您的选择对我们很重要。经审查，您的选择与我们的选择不一致。感谢您对设计一致性的贡献。」

二、libadwaita：主题问题的最好解决方案，是让主题问题消失。

如果用户能用主题改变按钮、边距和颜色，那么应用就可能出现不符合设计规范的样子。只要不让用户改变这些东西，这类问题便会大幅减少。从工程指标来看，这是一次辉煌的成功：问题数量下降了；从用户体验来看，用户也没那么多意见了——因为表达意见的通道已经被重新定义为不受支持的使用方式。

这套方案有一个潜在优势：它可以推广。比如，如果用户抱怨窗口不能按自己习惯排列，我们可以重新定义「窗口管理」；如果用户抱怨工作流被改变，我们可以重新定义「工作流」；如果用户抱怨升级以后扩展失效，我们可以重新定义「稳定」。等所有概念都重新定义完，指标就会漂亮得像一份没有用户参与的满意度调查。

System76 选择发展自己的桌面路线，Zorin OS 则通过插件补充部分定制能力。把这些事全都称为生态多样性当然没错，只是这种多样性很像：房东决定不修厨房水龙头，于是每个租户开始学习水管工程。房东由此证明了社区动手能力得到提升，租户则发现自己的周末没了。两边都成长了，只有水龙头依旧漏水。

三、GTK：通用工具包，附赠一份「非本桌面用户请自理」说明书。

GTK 当然可以优先服务 GNOME。上游没有义务满足所有人的需求，维护者也不需要把每一个提案都收进来供奉。但是，工具包一旦被大量非 GNOME 项目采用，路线选择就会产生外部成本。其他项目并没有参与创造每一个设计决定，却必须处理这些决定带来的影响。

这有点像一家水电公司对外宣布自己提供通用基础设施。你接入了它的管线，按规范交了钱，还给自己的房子装好了水龙头。某天公司宣布，未来的管径将按总部厨房的布局调整。你问能不能维持旧接口，对方回答：「当然可以继续使用我们的服务，但你的厨房不是我们的目标使用场景。」

严格来说，这句话并没有逻辑错误。你的厨房确实不是总部厨房。问题是，如果每个非 GNOME 用户都得先确认自己的需求是否属于「目标使用场景」，那么 GTK 的通用性就开始像商场里的「公共座椅」：谁都能坐，直到你真的坐下来，保安才告诉你这块区域用于展示空间美学。

笔者建议给 GTK 的项目介绍加一条醒目提示：「本工具包可供所有人使用。若您不是 GNOME 用户，建议在使用前确认自己的需求是否属于本项目未来愿意承认的需求。」这样既保留了开放性，也避免其他桌面环境误以为自己真的有参与生态规划的义务。

四、社区治理：欢迎提出意见，本项目会把它们归档在「已知但不采纳」目录。

开源不是全民公投，维护者当然可以拒绝提案。真正值得吐槽的是，当社区讨论总是在重要方向确定之后才开始时，讨论便逐渐有了考古学的性质。大家不是在影响项目的未来，而是在挖掘项目为什么会变成现在这样。

这时，issue 的作用也发生了变化。它不再只是报告问题和讨论方案的地方，还可以作为决策遗址的出土文献。研究人员可以通过评论时间线判断：维护者何时已经决定不改、社区何时发现自己没能改变、以及「感谢反馈」是在第几楼出现的。

为提高效率，笔者建议新增一个标准模板：

「感谢您的建议。我们理解您的使用场景。该问题与我们的设计目标不一致，因此不会处理。若您仍然遇到该问题，请确认您已经阅读我们的设计目标。若您希望继续讨论，请在已有讨论中补充意见，以避免重复。若您发现已有讨论中已经有人提出相同意见，请不要重复。」

如此一来，社区反馈流程就实现了完整闭环：用户把问题提交进来，问题被解释清楚，解释被归档，用户学会了这个问题不会被解决。知识得到了传播，问题得到了管理，问题本身则得到了永久居留许可。

五、GTK 4 与 API 迁移：让我们为死者默哀，死者的下游项目请留下来结账。

API 当然需要演进。旧设计有缺陷，旧接口有技术债，删除它们也许是正确的工程选择。问题是，上游删除一段 API，只需要合并一个变更；下游迁移一个成熟应用，却可能要排查一堆构建问题、行为变化和视觉回归。两边都在做技术工作，只是「删除」和「迁移」的工时通常不会在同一张表上显示。

Budgie 曾经长期使用 GTK，后来选择离开；Inkscape 的维护者也曾公开谈及 GTK 4 迁移带来的压力。无论如何评价这些技术路线，这些例子至少提醒我们：上游的架构决定不只影响上游。它可能把下游原本排给新功能的时间，改成修复兼容性；把开发者想改善用户体验的精力，改成确保应用还能启动。

笔者建议为每次大规模 API 迁移举行追悼会。主持人先介绍旧 API 生前的贡献，再由上游代表宣布它已无法满足现代设计需求，需要被正式移除。现场掌声雷动。

下游开发者随后上台，负责将仍然依赖旧接口的应用逐一迁移。发行版维护者负责修复构建问题，扩展作者负责恢复用户工作流，普通用户则负责在更新后向各个项目提交 bug 报告。

整个过程井然有序。唯一值得商榷的是，宣布旧 API 死亡的人不需要支付迁移费用，而负责迁移的人甚至可能不是当初使用这套 API 的人。

笔者建议，每次移除一个 API，都应当在发布说明中附上该接口的讣告、下游受影响项目清单，以及一张迁移成本结算单。结算方式可以很简单：上游获得架构整洁度，下游获得技术债，用户获得一次重新配置桌面的机会。

这就是自由软件的协作精神：有人负责决定进步，有人负责完成进步，还有人负责在进步完成之前继续使用旧版本。

六、GNOME Shell 扩展：恭喜你，开源社区又多了一位无薪值班工程师。

桌面升级之后扩展可能失效，这并不奇怪。真正奇怪的是，扩展作者经常需要承担一套类似值班工程师的工作：跟踪上游 API，适配新版本，处理用户反馈，修复回归，然后在下次更新时重新来一遍。

不同之处在于，值班工程师通常有工资、排班表和事故复盘；扩展作者可能只有一个 GitHub 仓库，以及十几条「大佬什么时候更新」的评论。

用户只知道自己的面板不见了。扩展作者知道上游改了什么。发行版知道包在哪个版本。桌面环境知道自己发布了新版本。所有相关方都掌握着一部分信息，最后由最没有资源的那个人负责把它们拼起来。这大概是分布式系统最真实的一次社会实验。

当然，KDE 的扩展也会坏。笔者并不打算因为 GNOME 的问题就给 KDE 颁发「永不破坏兼容性」奖章；真要颁这个奖，估计只能颁给还没发布第一个版本的桌面环境。区别在于，别人也有问题，只能说明大家都该改善，不能证明问题已经被解决。

七、应用分发：平台替用户做决定，用户感谢平台替自己省去了决定。

围绕 Flathub 对 LLM 相关应用的上架与审核争议，关键不在于应用商店是否应该有规则。平台当然需要审核、分类和安全政策。关键在于，规则应该足够明确，让开发者知道为什么被拒绝，也让用户知道平台究竟在保护他们免受什么风险。

否则，应用商店就很容易从「帮用户找到软件」变成「替用户决定哪些软件值得被找到」。这看起来很方便：用户不需要阅读应用说明，不需要自己评估，只需要接受搜索结果里剩下的选项。如此强大的用户赋能功能，建议命名为「代办式自主权」——用户依然拥有自主权，只是平台已经替他行使完了。

如果某款应用被拒绝，开发者可以申诉；如果申诉失败，还可以写邮件；如果邮件也没用，至少可以在自己的博客解释这次经历。用户则可以在平台里搜索其他应用。三方都获得了表达自由，应用本身则继续不存在于商店里。

这不是审查，这只是一次非常成功的内容可见性优化。至于具体审核标准和适用情况，请以平台公开规则为准；笑话可以夸张，事实最好不要跟着一起下架。


附录 A：一份虚构的 GNOME 用户支持工单

以下为讽刺性虚构对话，不是真实项目的客服记录。

用户：我想让应用跟随系统深色主题。

支持：应用不支持这种主题覆盖方式。

用户：能否增加支持？

支持：这不符合我们的设计目标。

用户：那我能不能自己改？

支持：您可以自由修改源代码，但这不属于受支持的用法。

用户：那「自由」具体体现在哪里？

支持：您可以自由选择是否继续使用本应用。

用户：我换成了另一个桌面环境。

支持：很高兴我们的设计帮助您做出了适合自己的选择。

工单状态：已解决。

解决方式：用户离开。

这个工单当然是编的。但它最讽刺的地方在于，里面没有一句话必须是谎话：维护者可以不支持某种用法，用户也确实可以离开。问题在于，当「你可以离开」成为处理所有分歧的万能答案时，项目就很容易把用户流失当成需求管理的一部分。按这个逻辑，医院如果把所有病人都劝回家，也能宣布候诊时间大幅下降。

把这些问题放在一起看，最值得讨论的不是 GNOME 到底好不好用，而是谁决定规则、谁承担代价，以及项目是否愿意承认这两件事并不总是落在同一拨人身上。上游可以获得更整洁的架构，下游承担迁移成本，发行版维护补丁，扩展作者免费值班，用户在更新后搜索解决方案。每个人都完成了自己的工作，只有「让用户少折腾」这项工作，暂时没有分配到负责人。

如果把这种流程称为生态协作，那么这确实是一种很有创造力的协作模式：上游负责决定，下游负责适应，用户负责理解。整个过程无需强迫任何人，因为只要把成本放在别人身上，大家自然会发现自己的选择非常自由。

我们不反对 GNOME 有自己的设计哲学，不反对 GTK 清理旧 API，也不要求任何维护者接受所有功能请求。我们反对的是把「上游不想支持」包装成「用户不应该需要」，把「下游得自己迁移」包装成「技术必然进步」，再把用户离开包装成「选择权已充分保障」。如果这也叫以用户为中心，那圆规以圆心为中心，大概也能算一次人机交互革命。

笔者没有说 GNOME 是宗教。宗教至少会告诉你哪些行为属于禁忌；某些设计争议的特别之处在于，你可以先自由地修改主题，等你发现不受支持时，才知道自己刚才完成了一次异端行为。

电脑是用户的。维护者可以决定自己的项目怎么做，用户也可以决定自己不再使用它。唯一希望是：不要一边告诉用户「你有选择」，一边把用户选择的每条路都标成不受支持。否则所谓自由，最终只剩一个按钮：退出。
